PROJECT DETAILS:
- Title: AI-Driven Log Anomaly Detection System with Real-Time Root-Cause Analysis and 
  Recommendation Engine (Working name: LogSentry)

PROBLEM STATEMENT:
Large software systems generate log data far beyond manual review capacity. The earliest signs 
of failure are usually buried in these logs as subtle deviations, not explicit errors. Existing 
monitoring is reactive (alerts only after users are affected), and even where anomaly-detection 
research exists, it evaluates offline on static datasets and outputs only a raw anomaly score — 
with no root-cause pinpointing, no severity ranking, and no actionable guidance for engineers.

OBJECTIVES (3):
1. Reduce detection delay — catch early warning signs in logs before users notice anything is wrong.
2. Solve the "black box" problem — pinpoint the exact event where behaviour breaks from the norm, 
   not just flag "something's off."
3. Close the gap between detection and action — turn a raw anomaly score into a severity level 
   and a plain-language explanation engineers can act on.

RELATED WORK / LITERATURE (brief mentions):
- Xu et al., 2009 — PCA-based console log mining, introduced the HDFS benchmark dataset
- Du et al., 2017 — DeepLog: LSTM-based next-event prediction for log anomaly detection
- Meng et al., 2019 — LogAnomaly: semantic embeddings for sequential + quantitative anomalies
- Zhang et al., 2019 — LogRobust: attention-based Bi-LSTM robust to unstable log formats
- Le & Zhang, 2022 — empirical survey showing most systems lack real-time, explainable output
Research Gap: no existing system combines real-time detection + root-cause localization + 
plain-language recommendations in one deployable web application.

PROPOSED METHODOLOGY (5 stages — use this as the architecture/workflow slide):
1. Ingestion: Logging middleware (Winston) → Node/Express ingestion API → Redis queue (Bull) → 
   per-session windowing (grouped by Block ID)
2. Model Training & Inference: LSTM trained in Python/PyTorch on the Loghub HDFS dataset 
   (primary benchmark; BGL dataset as optional stretch extension), served via a FastAPI 
   microservice, predicting the next expected log event
3. Detection: Compare predicted vs. actual event → flag deviation → localize the exact 
   root-cause event → assign severity (Low / Medium / High)
4. Recommendation: Structured anomaly context sent to Gemini API → plain-language explanation 
   + suggested next steps (LLM explains only, never detects)
5. Visualization: Incidents stored in MongoDB → pushed via Socket.io → live React dashboard

TECH STACK (include as a dedicated slide with categorized layout):
- Frontend: React.js, Socket.io-client
- Backend: Node.js, Express.js, MongoDB (NoSQL), Redis + Bull (queueing)
- Machine Learning: Python, PyTorch (LSTM model), FastAPI (inference microservice)
- External API: Google Gemini API (explanation/recommendation layer)
- Dataset: Loghub HDFS (primary), BGL (optional extension)
- Deployment: Docker, hosted on Render/Railway/AWS

EXPECTED OUTCOMES / DELIVERABLES (4 points):
1. A reproducible HDFS preprocessing pipeline, a transition-based baseline, and an LSTM detector 
   evaluated with precision, recall, F1-score, false-positive rate, and latency
2. An application that identifies the exact event where a sequence becomes unlikely, calculates 
   an anomaly score, assigns severity, and groups related detections into incidents
3. A containerized Node/FastAPI/MongoDB/Redis backend streaming incidents to a React dashboard 
   showing timelines, scores, affected components, surrounding events, and expected-vs-observed behaviour
4. A constrained Gemini layer translating evidence into plain-language explanations and suggested 
   checks, demonstrated end-to-end with a live log replay and a deliberately triggered failure

Out of scope: third-party production integration, automated incident remediation, multi-tenant 
deployment, mobile app.
